# Plan: release CI — GitHub release on `v*` tag

**Type:** tooling / infrastructure
**Objective:** Pushing a `v*` tag builds the binaries in CI and publishes a GitHub
release whose notes are that version's `CHANGELOG.md` section, with the Linux binary
and the Windows `.exe` attached.
**Why:** Releases are hand-made today, and the docs contradict themselves — `CLAUDE.md`
claims a tag "triggers the release workflow" while both `CLAUDE.md` and `README.md`
state there is no GitHub CI. This plan makes the first sentence true, keeps the second
accurate for build/PR CI, and closes the backlog item *Clarifier le workflow de release*.
**Layer(s):** ci, docs (no Go code changes).

## Scope

**In scope:**
- `.github/workflows/release.yml` — triggered on `push: tags: v*` only.
  - Nix-based: `cachix/install-nix-action`, then `nix develop --command just ci`
    as the gate, then the build recipes in the same dev shell. The Justfile stays the
    single source of truth for the gates — CI adds no second definition.
  - Artifacts: `dsa-save-editor-<version>-linux-amd64`,
    `dsa-save-editor-<version>-windows-amd64.exe`, plus `SHA256SUMS`.
  - Release notes: the `## [X.Y.Z]` section extracted from the committed
    `CHANGELOG.md` (already generated by `just changelog` and reviewed before tagging).
    Missing section ⇒ the job fails rather than publishing an empty release.
- `Justfile` — `build-linux` and `build-windows` take an optional `version` argument
  and stamp it into `main.buildVersion` via `-ldflags`. Default stays `dev`, so local
  behaviour is unchanged.
- Docs: `CLAUDE.md`, `README.md`, `DESIGN.md` (release section), `.claude/plans/BACKLOG.md`.

**Out of scope:**
- A build/test CI on push or PR — release-on-tag only (user's call). pre-commit
  remains the local guard.
- Binary signing / notarisation, packaging into archives, checksum signing.
- The stale `version = "0.1.0"` in `flake.nix`: `nix build .#default` stamps that
  string into the binary. The release path does not use it (it builds through the
  Justfile with the tag), but `nix run` reports a wrong version. Flagged, not fixed
  here — it wants its own decision (single source of truth for the version).

## Technical decisions

- **Nix over `actions/setup-go`.** CI runs the exact toolchain and gates a developer
  runs (`just ci` in the dev shell). No duplicated Go version or lint config. Cost:
  a few minutes per tag, which a tag-only workflow can afford. No binary cache.
- **Build through `just`, not `nix build`.** `nix build .#default` cannot see the tag,
  and its `version` is hard-coded in the flake. Running the Justfile recipes inside
  `nix develop` gives the same pinned Go toolchain *and* correct version stamping.
- **Notes from `CHANGELOG.md`, not `git-cliff --latest`.** The changelog is committed
  and human-reviewed before the tag; regenerating in CI would need network access to
  the GitHub remote (see `cliff.toml`) and could produce notes that differ from the
  committed file.
- **`GITHUB_TOKEN` with `contents: write`** and `gh release create`. No third-party
  release action, no PAT.

## Atomic steps (each = 1 commit, gates green)

1. `docs(plans): plan the release CI` — this file.
2. `build: stamp the version into the release binaries` — Justfile `build-linux` /
   `build-windows` with a `version` argument (+ `Justfile` doc comments).
3. `ci: publish a GitHub release on v* tags` — the workflow.
4. `docs: document the release workflow` — `CLAUDE.md`, `README.md`, `DESIGN.md`,
   backlog item closed.

## Quality gates

- [ ] `nix develop --command just ci` green.
- [ ] `just build-linux 0.17.0` and `just build-windows 0.17.0` produce binaries in
      `dist/` reporting the right version (`--version`).
- [ ] The changelog-extraction snippet returns the v0.17.0 section verbatim when run
      against the committed `CHANGELOG.md`.
- [ ] Workflow YAML parses (`actionlint` if available, otherwise a YAML load).
- [ ] Docs no longer contradict each other on CI.
- [ ] Atomic commits on `ci/release-workflow`; the user reviews, merges and tags.

## Validation (user-side, after merge)

The workflow can only be proven by a real tag. First run: push `v0.18.0` (or re-run
on a throwaway tag) and check the release page has the notes and both binaries.
