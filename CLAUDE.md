# CLAUDE.md — project instructions

## Architecture

Read `DESIGN.md` first. It defines what belongs where and the invariants. All
decisions flow from it — chiefly: **pure Go, no CGO** (cross-compiles to Windows),
and **never corrupt a save** (read-only on open, atomic write, automatic backup,
game closed before writing).

## Working methods

- **Plan first.** Every change is planned before code, following
  `PROCEDURE_PLANS.md`. Plans live under `.claude/plans/` (`vX.Y.Z/` per release,
  `release/` for tooling), never at the repo root. See `.claude/plans/README.md`.
- **Hybrid git.** Work on a dedicated branch (`feat/…`, `fix/…`, `refactor/…`,
  `docs/…`, `chore/…`, `ci/…`, `build/…`), never on `main`. Commit atomically
  (Conventional Commits). **Never** merge, push, or tag — the user does that.
- **Releases.** SemVer, pre-1.0 (`0.x`): breaking changes bump the minor.
  `CHANGELOG.md` is generated by `git-cliff` (`just changelog`) and **committed before
  the tag** — pushing a `v*` tag runs `.github/workflows/release.yml`, which reuses
  that version's changelog section as the release notes and attaches the Linux and
  Windows binaries. No changelog section for the tag ⇒ the job fails.
  The order is not interchangeable:

  ```sh
  git pull                                       # rebase FIRST — see below
  git merge --no-ff <branch>                     # the plan branch
  git-cliff --tag vX.Y.Z --output CHANGELOG.md   # --tag labels the untagged commits
  git commit -am "docs: changelog for vX.Y.Z"    # the notes must be IN the tag
  git tag -a vX.Y.Z -m "vX.Y.Z"
  git push origin main                           # branch BEFORE tag
  git push origin vX.Y.Z                         # this is what triggers the workflow
  ```

  Two traps, both hit on v0.17.1: a `git pull --rebase` **after** tagging rewrites the
  commits and leaves the tag on an orphaned one (retag on the new `main`); and pushing
  the tag before `main` can leave GitHub with no workflow to run, so nothing fires.
- **Docs in the same commit** as the code they describe. A structural change without
  a doc update is a defect.

## Layers & scopes

```
internal/sqlcipher → internal/save → internal/web → cmd/dsa-save-editor
```

Lower layers never import higher ones. Commit scopes: `sqlcipher`, `save`, `web`,
`cmd`, `nix`, `docs`.

## Verification

```bash
nix develop                        # dev shell (go, staticcheck, just, nixfmt, pre-commit…)
just ci                            # fmt-check + vet + lint + test + build (Go gates)
just check                         # nix flake check (build + go test + gofmt)
DSA_SAVE=/path/to/6144_Slot1.db just test   # also round-trips a real save
just build-windows 0.17.0          # release-time cross-compile gate (.exe)
just build-linux 0.17.0            # release Linux binary (version stamped)
pre-commit install                 # run the gates automatically before each commit
```

`just` is the single source of truth for the gates — pre-commit, `nix flake check`
and the release workflow reuse the same recipes. There is **no build/PR CI** (by
choice): the only workflow is the release on a `v*` tag, and it runs `just ci` in
the Nix dev shell before publishing.

## Save safety

- Never write a save while the game is running (it holds the DB open).
- Real saves, `*.sav`, screenshots and backups are local fixtures — never commit
  them. Reference a real save through `DSA_SAVE`.
